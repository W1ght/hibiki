## BUG-2572 · Windows 看番时键鼠随机失灵、视频照播，开小内存模式后消失
- **报告**：2026-09-16（用户转述群友：Windows 桌面「进视频界面以后会随机卡死，具体表现是导航条消失以后视频仍在播放但是无法操作」，键鼠都没反应，此前还「卡卡的」；更新到最新版仍复现；40 GB 内存；**开小内存模式后不再出现**；另有群友同症状。是否首次打开 / 是否全屏 / 卡死前有没有查过词，报告人未答）
- **真实性**：❌ **未复现**（本机离屏 Windows runner 真 app 两轮探针都走不出「输入死、视频活」的态）。沿真实代码路径能钉死的只有这一条：**小内存模式对视频播放页的全部影响 = 查词浮层 controller 的 `lowMemory`**（`fushi/lib/src/pages/implementations/video_fushi_page.dart:4879` `_seedWarmPopup` 唯一读取点）+ 三层全局缓存预算（`app_model.dart:8279` imageCache 100 MB→20 MB、`dictionary_repository.dart:381-401` 词典三缓存、`app_model.dart:1762` 查词历史 5/10）+ 启动期 headless WebView 预热（`main.dart:544`）。播放管线（`media/video/` 72 文件、`video_fushi/` 全部 part、mpv 配置、缩略图、字幕 / 弹幕 / OCR）**零处**读该开关。也就是说，小内存模式在视频页关掉的东西只有一样：**常驻屏外隐藏的查词热槽 WebView2**（`dictionary_popup_controller.dart:324` `seedWarmSlot` 在 `lowMemory` 时早退；`:663` `dismissAt(0)` 在 `lowMemory` 时清栈销毁而不是停靠保留）。Windows 上这是 composition 模式的 WebView2：主窗口的隐藏 owned 顶层窗 `CustomPlatformView`（`packages/flutter_inappwebview_windows/windows/in_app_webview/in_app_webview_manager.cpp:145`）内含隐藏 `Chrome_WidgetWin_0`，WGC 抓帧泵以 60 Hz DispatcherQueueTimer 跑在平台线程（`texture_bridge.cc:23` `kPumpInterval100ns`，3.44 引擎默认平台 / UI 线程合并）。
  - **已否定的假设**（都有本机真 app 证据，`fushi/integration_test/video_warm_slot_win32_focus_probe_itest.dart`，证据目录 `fushi/.codex-test/windows-itest/win-itest-20260916-171520-*` 与 `-181918-*`）：
    1. 「热槽的隐藏 Chrome 窗口拿走 Win32 键盘焦点 / 鼠标捕获」——查词 → 把一次鼠标点击经 fork 真实转发进 WebView2 → Esc 关弹窗，全程 `GetFocus` 恒为 `FLUTTERVIEW`、`GetCapture` 恒空、`GetActiveWindow` 恒主窗口，热槽与小内存两态一致；把 `WM_KEYDOWN(VK_SPACE)` 投给 `GetFocus()` 两态都能暂停 / 续播视频。caveat：runner 窗口 `WS_EX_NOACTIVATE` 且不在前台，WebView2 在**前台 app** 里被点击时是否会 `SetFocus` 到自己的 HWND，本机没有验证；但同一机制在阅读器（热槽 + 正文 WebView2）会让每次关弹窗后方向键翻页也死，没有这类报告，故该假设可信度很低。
    2. 「隐藏热槽在后台驱动帧 / 吃 CPU（解释卡顿）」——视频暂停、无动画时统计 5 s：热槽 `frames=1 cpuMs=203`，小内存 `frames=1 cpuMs=218`，无差异；popup.css 无常驻 `@keyframes`。
    3. 「热槽 entry 身份永久不变 → 查词异步结果迟到复活弹窗」——逐条读 `pushNestedPopup`（`dictionary_page_mixin.dart:990-1100`）/ `dismissAt` / `_restoreWarmSeed` / `markPendingReveal` 兜底 Timer：`dismissAt(0)` 只会在有可见层时被调到，搜索期 barrier 点击走 `_popNestedPopupAt(-1)` 是 no-op，两态行为一致，且所有终态都能被再一次点击 / 按键关掉，不构成「无法操作」。
    4. 「浮层 entry 每帧 markNeedsBuild 往 WebView2 灌 JS」——`DictionaryPopupInputSpec` 有值相等（`dictionary_popup_input_bridge.dart:43`），`didUpdateWidget` 三条注入门全部 no-op。
  - **仍未验证的鼠标链路**：探针把真 `WM_MOUSEMOVE` 投给 `FLUTTERVIEW` 在两态下都**没能**唤起 media_kit 控制条（阳性对照失败：离屏 no-activate 窗口里这条注入路径本身不通），所以「关弹窗 / 长空闲后鼠标移动能否唤回导航条」在本机仍是盲区；需要前台真机（或让 runner 临时前台）才能测。
- **[ ] ① 未修复** — 没有可指认的根因，不做盲改。当前可靠的规避就是报告人已发现的「设置 → 其他设置 → 小内存模式」（它对视频页的实际语义 = 不常驻热槽 WebView2，每次查词冷开弹窗、多一瞬白屏）。
- **[ ] ② 未加自动化测试** — 探针 itest 留在本条分支作为复现脚手架（不是回归测试，不进 CI 单测门）。
- **备注**：下一步要从报告人拿到再定性——① `%LOCALAPPDATA%\Fushi\wgc_capture.log`（WGC 结构化日志，看卡死时段有无 `frame-getfail` / `pump-late-noop` / `recreate` 风暴）与 app 错误日志；② 卡死前是否查过词 / 是否全屏 / 是否第一次打开视频就卡；③ 卡死时 Alt+Tab 切走再切回、或点一下画面能否恢复；④ WebView2 Runtime 版本与显卡。若 ① 在卡死时段显示热槽池被反复 `recreate`，或 ③ 显示切窗即恢复，则分别指向 WGC 会话与 Win32 焦点两条线，届时再在前台真机上复跑本探针。
