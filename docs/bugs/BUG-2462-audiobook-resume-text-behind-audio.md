## BUG-2462 · 有声书重开书正文恢复点落后于音频位置
- **报告**：2026-09-12（用户：「书重新打开有可能和有声书阅读进度错误，可能落在当前进度前面但是有声书在后面，一旦播放就会跨了很多页导致阅读速度和阅读量异常」）
- **真实性**：✅ 真 bug。开书时正文位置与音频位置**各自独立恢复、没有任何对账**：正文从 `reader_positions` 恢复（`fushi/lib/src/pages/implementations/reader_fushi_page.dart` `_initBookInner` 的存档分支，只在「无保存位置」时才 `_restoreFromCurrentAudioCue`），音频从 `audiobook_pos_<key>` 偏好恢复（`audiobook_session_launcher.dart` `_readPrefs` → `AudiobookPlayerController.load(initialPositionMs)`）。正文位置只在阅读器页活着时随滚动 / 跟随 reveal 落库（`navigation.part.dart` `_syncPositionFromCurrentCue` 只在 reveal=true 调），音频位置由会话**每秒**落库（`audiobook_controller.dart` `_maybeSavePosition`），且「后台续播」开关下退出阅读页**不 stop 会话**（`audiobook_exit_stop_policy_static_test.dart` 钉死）——退书后台听、锁屏听完一章、换端听过，音频跑远了，正文还停在退出那一刻。重开书正文按旧位置恢复，一按播放 `shouldRevealCurrentCue` 转真，音频单向把正文拽到几十页之外。
  - 对统计的影响：分页模式下账本（`ReadUnitLedger`）只计翻走的单元，这一跳本身不计跳过的页；**连续模式**的跟随是 smooth 长距离滚动，途中视口被逐个 arrive 进账本——那是另一根因，见 BUG-2463。但无论哪种模式，这一跳都让用户看到「进度错了 / 一播放就翻几十页」。
- **[x] ① 已修复** — 提交见合并记录。**谁新谁赢**（`fushi/lib/src/media/audiobook/audiobook_resume_reconcile.dart` 纯判据）：存档分支先 `_audioPositionOutranksSaved(saved)`（`audiobook.part.dart`）——用 `AudiobookSessionLauncher.resolvePrefsKey` 拿会话 prefs 键（EPUB = bookKey、字幕书 = uid），读 `audiobook_pos_at_<key>` 与 `reader_positions.updatedAt` 比：音频新出 `kAudiobookResumeGraceMs`（3s，退书时正文先 flush、音频后 flush 天然差几百毫秒）以上且本书开着「跟随音频」（关着 = 有意分离，不动）才判真；这一步只读 pref、**不等音频槽**（槽刻意不挡首屏）。判真后才 `await audioSlotFuture`，`_audioCueStartOutrankingSaved` 用 `_positionFromCurrentAudioCue`（从原 `_restoreFromCurrentAudioCue` 抽出，老路与新路共用）推 cue 起点：能定到章内位置（sasayaki 片段 / SRT 章内比例，`precise`）或至少章不同，且与保存位置隔得够远（`readerPositionsFarApart`：不同章即远，同章 `|Δprogress| × 章字数 ≥ 600 字`，约一页手机屏；同一页内保留带精确锚的保存位置），才 `_applyAudioCueStart`（锚 -1，走 `restoreProgress(分数)`）。正文更新（用户静读到前面去了）一律不动。每次决策进统计诊断流水（`studyDiag('reader', 'open … audioNewer=…')` / `resume from audio cue …`）。
- **[x] ② 已加自动化测试** — `fushi/test/media/audiobook/audiobook_resume_reconcile_test.dart`：两条纯判据（宽限 / 缺时间戳 / 不同章 / 同章按字数 / 章字数未知退万分比）+ 源码守卫（存档分支必须先问时间戳判据 → 判真才等槽 → cue 起点 → 应用，判否走原精确锚分支；判据只读 pref、看跟随开关、不碰音频槽；不精确且同章不换；老路新路共用同一推导；cue 派生锚 -1）。真 app：`fushi/integration_test/audiobook_resume_align_itest.dart` 段 A——正文位置存 5%、3.5s 后音频位置写到第 90 句（≈ 90%），重开书**不按播放**，落库的阅读位置收敛到 > 50%、会话未播放、流水记 `resume from audio cue chapter=0 … (audio position newer)`；段 B 负向对照——正文位置更新时保留 5%、流水记 `audioNewer=false`。Windows 离屏 / Mac 跨机同一份。
- **备注**：反方向（正文比音频新，用户静读到前面、按播放被拽回）不在本条范围，现状不变（`snapReaderToAudio` 跟随语义）；流水里能看到。旧 `[data-cue-id]` 片段 / 章级兜底 cue 只知道章：同章不换起点（保存位置更准），不同章落到音频所在章章首。`_chapterCharCounts` 未就绪（旧书导入无计数、后台重算中）时精确分支进度为 0、判「不远」，保留保存位置——宁可不动。
